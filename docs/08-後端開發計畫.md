## 1. 範圍與原則

後端承擔本案**全部業務規則**（R1–R9）、資料正確性與個資保護責任。

| # | 原則 | 說明 |
|---|---|---|
| **B-1** | **規則只實作一次** | 民國日期、時間進位、地址對調、趟數展開各只有一個函式，匯出、預覽、報表全部共用。禁止在 SQL 與 Go 各寫一份 |
| **B-2** | **原始資料永不覆蓋** | `form_submissions.payload` 只寫不改；正規化與合併結果可重算。任何匯入邏輯修正都能重跑歷史資料 |
| **B-3** | **不確定就不猜** | 欄位對應不到、混車衝突、司機姓名比對不到，一律進待處理佇列，不自動裁決、不靜默忽略 |
| **B-4** | **約束下沉到資料庫** | 更正必附操作者、同車同期不得有兩位主要司機等，由 `CHECK` 與 `EXCLUDE` 保證，應用層檢查只是第二道 |

## 2. 技術選型與套件清單

框架已於文件 02 §2 定案（Go 1.23 + Gin + Cloud Run），此處補齊相依清單。

| 用途 | 套件 | 說明 |
|---|---|---|
| HTTP 框架 | `github.com/gin-gonic/gin` | 文件 02 已定 |
| 資料庫驅動 | `github.com/jackc/pgx/v5`（含 `pgxpool`） | 原生 PostgreSQL 型別支援（`SMALLINT[]`、`JSONB`、`daterange`），本案大量使用 |
| 查詢產生 | `sqlc` | 由 SQL 產出型別安全的 Go 函式。**不用 ORM**：本案查詢以報表式 join 為主，ORM 反而礙事；`sqlc` 讓 SQL 保持可讀、又不必手寫 scan |
| Migration | `github.com/golang-migrate/migrate/v4` | 文件 02 §5.3 的 migration job |
| Excel | `github.com/xuri/excelize/v2` | 產生政府申報表 `.xlsx`、趟數表、時刻表、空白保養表 |
| Google API | `google.golang.org/api/sheets/v4`、`google.golang.org/api/forms/v1` | 每日對帳軌、表單改版輔助 |
| JWT 驗證 | `github.com/golang-jwt/jwt/v5` + `github.com/MicahParks/keyfunc/v3` | 驗 Supabase JWT（JWKS 快取） |
| Email | `github.com/resend/resend-go/v2` | F4 未回報通知、F10 請假通知 |
| 設定 | `github.com/kelseyhightower/envconfig` | 全部設定走環境變數，配合 Cloud Run `--set-secrets` |
| 日誌 | 標準庫 `log/slog`（JSON handler） | Cloud Logging 直接解析結構化欄位 |
| 錯誤追蹤 | `github.com/getsentry/sentry-go` | |
| 測試 | `github.com/stretchr/testify`、`github.com/ory/dockertest/v3` | 單元與整合測試 |
| 文件 | `github.com/swaggo/swag` + `gin-swagger` | 產出 OpenAPI 供前端產型別（見 §6） |
| 中文正規化 | `golang.org/x/text/unicode/norm` | NFKC + 異體字處理（罕用字 `𣵛`、`温`/`溫`） |

> **不引入**：GORM 或 ent（與 `sqlc` 重疊）、自寫排程器（Cloud Scheduler 負責）、訊息佇列（匯出用 Cloud Run Job 即可，不需 Pub/Sub）。

## 3. 分層架構

```
apps/api/
├── cmd/
│   ├── server/main.go          # REST API 進入點
│   ├── exporter/main.go        # Cloud Run Job：報表產生
│   └── migrate/main.go         # Cloud Run Job：migration
├── internal/
│   ├── config/                 # envconfig
│   ├── domain/                 # 純業務規則，無任何 I/O
│   │   ├── rocdate/            # R2 民國日期
│   │   ├── timeslot/           # R3 服務時段與跨小時進位
│   │   ├── namenorm/           # 姓名 Unicode 正規化與模糊比對
│   │   ├── crypto/             # 身分證 AES-256-GCM + HMAC 索引
│   │   ├── merge/              # R5 混車合併
│   │   ├── calendar/           # R4/R6/R8 應搭乘日曆與趟數展開
│   │   └── govform/            # 33 欄對應與排序
│   ├── repository/             # sqlc 產出 + 手寫複雜查詢
│   ├── service/                # 用例層：主檔、匯入、匯出、通知
│   ├── export/                 # excelize 樣板與檔案產生
│   ├── ingest/                 # webhook 解析、Sheets 同步
│   ├── handler/                # Gin route 與 Controller
│   └── middleware/             # 認證、角色、稽核、請求日誌
├── migrations/
├── queries/                    # sqlc 的 .sql 來源
└── testdata/                   # 去識別化樣本（黃金檔案測試）
```

**依賴方向單向**：模組內 `transport → app → infra`（`infra` 實作 `app` 宣告的 port），`domain` 不依賴任何其他層。`domain` 底下每個套件都能單獨測試、不需資料庫，這正是 R1–R9 能被高覆蓋率測試保護的原因。

## 6. API 契約產出

前端需要穩定契約才能平行開發（文件 07 §6）。作法：

1. 所有 handler 加 `swaggo` 註解（含請求／回應結構與錯誤碼）。
2. `make docs` 產出 `docs/swagger.json`，隨服務部署至 staging 的 `/swagger/doc.json`。
3. **Sprint 1 結束前先把主檔 CRUD 的 DTO 定義出來**，即使 handler 尚未實作完，也要讓前端能產型別。
4. 契約變更走 PR，`swagger.json` 的 diff 即為變更說明；破壞性變更需在 PR 標題註明並通知前端。

回應格式統一（文件 03 §5）：

```jsonc
{ "data": { }, "meta": { "page": 1, "total": 235 } }
{ "error": { "code": "PRECHECK_FAILED", "message": "...", "details": [ ] } }
```

`code` 需集中定義成常數，前端可依 `code` 分支處理，不解析 `message` 文字。

## 7. 測試策略

| 層級 | 範圍 | 工具 | 判準 |
|---|---|---|---|
| 單元 | `domain/` 全部套件 | `testing` + `testify` | **覆蓋率 ≥ 90%**，`rocdate`／`crypto`／`namenorm` 要求 100% |
| 黃金檔案 | 33 欄匯出 | Go golden file | 產出與 `蔡曾切11507` 期望值逐格相等 |
| 整合 | 匯入 → 合併 → 匯出全鏈路 | `dockertest` + Postgres | 跑真實樣本結構 |
| API | 權限、驗證、錯誤格式 | `httptest` | 401／403／400 各有案例 |

**測試資料一律去識別化後才進 Git**（文件 04 §4）：身分證改為合法格式假號、地址虛構、姓名代號化，但**保留罕用字、異體字、序號重複、去回程不成對等邊界特徵**——這些正是要測的東西。原始檔存放於客戶指定的加密位置，不進版控。

## 8. 部署與維運

| 項目 | 設定 |
|---|---|
| 區域 | `asia-east1`（彰化） |
| Cloud Run api | `--min-instances 0 --max-instances 5 --memory 512Mi --timeout 900 --allow-unauthenticated`（前端 SPA 直接帶 Supabase JWT 呼叫，身分驗證改由 `AuthMiddleware` 驗證 JWKS 簽章負責，而非 GCP IAM） |

| 尖峰調整 | 每月 26 日～次月 5 日視情況把 `min-instances` 調為 1，避免冷啟動 |

## 9. 後端對應的驗收條件

文件 04 §3 中由後端負責證明的部分：

- [ ] AC-2：竹北一車全月匯入的 `ride_records` 筆數與人工計算一致。
- [ ] AC-2：4 趟個案勾選有坐時展開為 4 筆 leg；單向個案不虛增反向趟次。
- [ ] AC-2：混車跨表單正確合併；兩車皆有坐時進衝突清單。
- [ ] AC-2：衝突經人工裁決後重跑同步**不被覆蓋**。
- [ ] AC-2：罕用字與異體字不造成對應失敗。
- [ ] AC-2：未知欄位的資料完整存於 `form_submissions.payload` 並發出待對應通知。
- [ ] AC-3：`蔡曾切11507` 39 列 × 33 欄逐格一致（黃金檔案測試）。
- [ ] AC-3：不同單價與不同服務時長的個案，第 6、10、11 欄各自正確。
- [ ] AC-3：09:55 + 10 分的第 10 欄為 `10`、第 11 欄為 `5`。
- [ ] AC-4：缺里程時匯出被擋，錯誤指出個案與欄位。
- [ ] AC-4：更正未填原因仍可成功；`corrected_by` 缺漏時資料庫 `CHECK` 擋下。
- [ ] AC-4：更正過的紀錄重跑表單同步後不被覆蓋，且回傳 `sourceChanged` 提示。
- [ ] AC-4：稽核可查出「誰、何時、把哪一筆從沒坐改成有坐、原因為何」。
- [ ] AC-5：全部個案一個月匯出 < 30 秒；資料庫每日備份已驗證可還原。
