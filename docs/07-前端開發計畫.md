## 1. 範圍與原則

前端是**純 API 客戶端**：不含任何業務規則運算（R1–R9 全部在後端），只負責畫面、輸入驗證、狀態呈現與檔案下載。

三條貫穿全案的原則：

| # | 原則 | 說明 |
|---|---|---|
| **P-1** | **能用套件就不手刻** | 表格、表單、彈窗、日期選擇、上傳、圖表、圖示一律用 Element Plus 與 ECharts 現成元件。禁止自行實作分頁器、下拉選單、日期元件、Modal、Toast |
| **P-2** | **不自訂 CSS 框架** | 版面用 `el-container` / `el-row` / `el-col`，間距與色彩用 Element Plus 的 SCSS 變數覆寫。全案手寫 CSS 只允許三處例外（見 §4.3） |
| **P-3** | **業務判斷不進前端** | 前端不算民國年、不判斷該不該申報、不決定衝突優劣。所有判斷結果由 API 給，前端只渲染 |

> P-3 是交接性的關鍵。行政人員報「數字錯了」時，除錯範圍永遠只在後端一處，不會出現前後端各算一次、算法不同步的問題。

## 4. 基礎建設

### 4.1 API 層

`api/client.ts` 單一 Axios instance，攔截器負責四件事：

1. 附加 Supabase JWT（過期自動更新後重送一次）
2. `401` → 清除登入狀態並導回 `/login`
3. `403` → 顯示「權限不足」，不導頁
4. 其餘錯誤 → 取 `error.message` 丟 `ElMessage.error`，`error.details` 有內容時改用 `ElNotification` 條列

各資源的 API 函式一律寫成 `export async function listCases(params: ListCasesParams): Promise<Paged<CaseDTO>>`，**型別取自 `types/api.d.ts`**，不自行宣告。

### 4.2 權限

- 路由 `meta.roles: ('admin' | 'staff' | 'viewer')[]`，`guards.ts` 統一比對，不足即導向 403 頁。
- 畫面層以 `v-if="auth.can('staff')"` 控制編輯按鈕顯示。
- **前端權限只是體驗，不是防線**；後端 middleware 為準（文件 03 §5）。

### 4.3 樣式

只覆寫 Element Plus 的 SCSS 變數（主色、圓角、表格密度），全案手寫 CSS 僅允許以下三處：

| 例外 | 原因 |
|---|---|
| 搭乘月曆的格子狀態色 | `el-table` 的 `cell-style` 需要色票，屬資料驅動樣式 |
| 列印樣式（`@media print`） | 新竹時刻表需 A4 橫式列印 |
| 登入頁置中版面 | 不套用 `DefaultLayout` 的唯一頁面 |

其餘任何自訂 CSS 需求，先確認 Element Plus 是否已有對應元件或屬性。

### 4.4 共用行為

| 行為 | 統一作法 |
|---|---|
| 清單頁查詢條件 | `useListQuery` 同步到網址 query，重新整理不遺失條件 |
| 表單驗證 | `el-form` 的 `rules`，必填、格式、數值範圍全部宣告在 `rules` 物件內 |
| 危險操作 | `ElMessageBox.confirm`，刪除、覆寫、開關系統旗標一律二次確認 |
| 長時間作業 | 匯出採輪詢 `GET /exports/{jobId}`，畫面用 `el-progress` + `el-result` |
| 身分證顯示 | 一律用 `MaskedId.vue`，禁止在頁面直接輸出完整身分證字串 |

## 6. 與後端的介接

前後端要能分開推進，靠兩件事：**先有契約**、**契約可跑**。

### 6.1 型別產生

後端以 `swaggo` 註解產出 OpenAPI（見文件 08 §6），前端執行：

```bash
npm run gen:types
```

該指令內容為 `openapi-typescript $VITE_API_SPEC_URL -o src/types/api.d.ts`，來源是**已部署 staging 的 `/swagger/doc.json` 網址**，不讀取 `apps/api/` 目錄，維持文件 02 §5.2 的零跨目錄依賴。產出檔納入版控，PR 中可直接看出契約變更。

### 6.2 平行開發

| 階段 | 前端資料來源 |
|---|---|
| 後端該支 API 未完成 | `msw` handler 回傳依 `api.d.ts` 型別寫的假資料 |
| 後端已上 staging | `.env.development` 指向 staging，關閉 `msw` |
| 本機同時開發 | `vite.config.ts` 的 `server.proxy` 把 `/api` 轉發至 `localhost:8080` |

假資料**必須涵蓋邊界情況**：4 趟個案、單向個案、含衝突的搭乘紀錄、已更正且來源事後變更的紀錄（`sourceChanged`）、含 error 的檢核結果、通知收件人為空的狀態。這些情境在真實環境不容易重現，用 mock 反而更好測。

### 6.3 交界檢查點

| 時間 | 檢查點 |
|---|---|
| Sprint 1 結束 | 契約凍結第一版：主檔 CRUD 的請求與回應格式雙方確認 |
| Sprint 2 結束 | 前端能打通 staging 的個案 CRUD，不再依賴 mock |
| Sprint 3 中 | 搭乘月曆的資料結構（月 × 個案 × leg）雙方對過一次；此結構若晚改，前端月曆需重寫 |
| Sprint 4 初 | 匯出工作的狀態機（pending／running／succeeded／failed）與檢核結果格式確認 |

> Sprint 3 那一項風險最高。月曆是全案最重的畫面，**資料結構務必在動工前談定**。

## 7. 測試與品質

| 層級 | 範圍 | 工具 |
|---|---|---|
| 型別 | 全專案 | `vue-tsc --noEmit`，CI 必過 |
| 靜態檢查 | 全專案 | ESLint + Prettier，CI 必過 |
| E2E | 五條關鍵流程 | Playwright |
| 手動 | 各頁 CRUD 與權限 | UAT 前自測清單 |

依文件 04 §4，前端**不寫元件單元測試**，改以 E2E 覆蓋五條關鍵流程：

1. 登入 → 依角色看到不同選單
2. 個案建檔 → 排班設定 → 出現在搭乘月曆
3. 欄位對應：待對應欄位 → 綁定個案 → 狀態轉 `mapped`
4. 搭乘紀錄更正：改狀態後月曆記號變更、司機原始回報仍可見、未填原因也能送出
5. 匯出：檢核有 error 時被擋 → 修正後成功產檔並可下載

E2E 一律打 staging 或 `msw`，**不連正式環境**。

## 8. 交接性規範

以團隊接手為前提的硬性規定：

1. **元件單檔不超過 400 行**，超過就拆成 `components/` 下的子元件。
2. **`views/` 內不得出現 `axios`**，一律經 `api/` 的函式。
3. **`types/api.d.ts` 禁止手改**，契約要改就改後端再重新產生。
4. **中文字串集中在 `types/domain.ts` 的標籤對照表**（如 `boarded → 有坐`），不散落在模板裡。
5. **Pinia 只有 `auth` 一個 store**；伺服器資料由頁面自取，新增 store 需在 PR 說明理由。
6. **註解只寫「為什麼」**，不翻譯程式碼本身在做什麼。
7. `README.md` 記錄環境變數、啟動指令、產型別指令三件事，新人照著跑得起來即為合格。

## 9. 前端對應的驗收條件

文件 04 §3 的驗收條件中，由前端負責證明的部分：

- [ ] AC-1：欄位對應頁能顯示 15 份表單的 `pending` 數，並支援逐筆綁定至 0。
- [ ] AC-2：搭乘月曆能正確呈現 4 趟個案的四個時段、單向個案不顯示反向時段、衝突格有明確標示。
- [ ] AC-3：匯出頁能完成「選範圍 → 檢核 → 產檔 → 下載」全程，下載連結為簽章 URL。
- [ ] AC-4：更正面板同時顯示司機原始回報與更正後的值；改出發時間時標示與排班設定的差異。
- [ ] AC-4：個案與司機清單身分證預設遮罩，「顯示完整」需點選觸發。
- [ ] AC-5：全部個案清單頁（約 200 筆）分頁載入無明顯延遲；月曆矩陣（200 列 × 31 欄）可正常捲動。
