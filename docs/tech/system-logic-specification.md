## 準則一：主檔基本資料管理規範（CRUD 與啟用／停用狀態）

系統內所有主檔實體（Master Data）均必須具備完整生命週期管理，不得存在僅可新增無法修改、或僅能硬刪除而無法停用的半套設計。

### 1.1 涵蓋主檔範圍
- **個案主檔 (`cases`)**：個案基本資料、身分證號、身分別、福利身分、聯絡資訊等。
- **司機主檔 (`drivers`)**：駕駛姓名、聯絡電話、駕照類別與到期日等。
- **車輛主檔 (`vehicles`)**：車牌號碼、廠牌型號、所屬單位、出廠年月、保險到期日等。
- **照服員主檔 (`caregivers`)**：照護人員姓名、類型、任職資訊等。
- **服務據點／單位主檔 (`sites`)**：據點名稱、所屬行政區、營運地址、每週開放日等。
- **使用者與權限帳號 (`users`)**：系統使用者、所屬角色、權限配置等。

### 1.2 完整 CRUD 必備功能
1. **新增 (Create)**：
   - 提供專屬建立對話框或頁面，前端進行必填欄位與格式即時校驗。
   - 後端進行業務唯一性（如身分證 HMAC、車牌號碼）與合法性校驗。
   - 新增時預設狀態為「啟用 (`active`)」。
2. **查詢與檢視 (Read / List / Detail)**：
   - 列表支援分頁、關鍵字搜尋、行政區域篩選、狀態篩選（全部／啟用／停用）。
   - 提供單筆明細檢視與歷史稽核歷程（更新時間、操作人員）。
3. **編輯 (Update)**：
   - 支援完整修改，禁止將使用者已維護好的有效欄位清空。
   - 具備防競態條件（Optimistic Locking / `updated_at` 比對），防止多人同時覆寫。
4. **刪除與停用 (Delete / Deactivate)**：
   - 一律使用軟刪除（`deleted_at`），禁止物理硬刪除，確保稽核軌跡與外鍵關聯完整。
   - **軟刪除與停用是兩種不同的終結語意，不可混用**：

     | 手段 | 欄位 | 全站可見度 | 使用時機 |
     |---|---|---|---|
     | **停用** | `status = 'inactive'` | 營運介面排除（見 §1.3），**歷史趟次、月結報表與申報資料完整保留** | 實體已不再營運，但歷史紀錄必須留在報表中 |
     | **刪除** | `deleted_at IS NOT NULL` | **全站排除，含歷史報表與政府申報** | 建錯的資料、測試資料，或確定要讓該實體從所有報表消失 |

   - 選擇「刪除」代表接受該實體的歷史趟數會從趟數表、儀表板與申報檔一併消失；需要保留歷史數字時一律改用「停用」。
   - 所有查詢 `vehicles`／`drivers`／`cases`／`sites` 的 SQL 都必須帶上 `deleted_at IS NULL`：主體查詢整列排除，僅取顯示名稱的 `LEFT JOIN` 則把條件寫進 `ON` 子句讓名稱留白，不可依賴前端隱藏。

### 1.3 啟用／停用（Active / Inactive）狀態行為準則
- **狀態欄位規格**：
  - 資料庫與 API 統一使用 `status` 欄位（列舉值：`active` 啟用、`inactive` 停用）。
  - 前端清單列提供直覺的操作控制項（如 Switch 開關或下拉選單），點擊切換時需跳出二次確認彈窗，說明停用後之影響。
- **停用狀態的業務限制**：
  - **即時營運排除**：處於「停用」狀態的實體，在所有排程、指派、派車與業務下拉選單中**一律不予顯示或不得選取**（例如：停用的司機不可被指派至車輛、停用的車輛不可進行日曆排班、停用的個案不可產生新的應搭紀錄）。
  - **歷史資料保留**：歷史已發生的趟次、月結報表與統計資料中，必須完整保留該實體的歷史名稱與記錄，不得因停用而變為空值或遺失。這是「停用」相對於「刪除」的關鍵差異（見 §1.2.4）。
  - **可逆性**：管理者可隨時將「停用」狀態變更回「啟用」，恢復其在業務介面中的可用性。

## 準則二：資料匯出規範（前置檢核、缺漏標示、快捷修正與非阻擋原則）

為確保報表與申報資料品質，同時兼顧使用者在緊急或特例情境下的操作彈性，匯出功能必須提供前置檢核與非阻擋設計。

### 2.1 匯出前自動前置檢核（Pre-export Check）
- 使用者在點擊「匯出」按鈕時，系統於產生最終匯出檔案（如政府申報 Excel、趟次月結表）前，必須先觸發前置檢核機制。
- 檢核維度包含：
  - **基礎資料完整性**：如個案缺身分證字號、缺住家地址、缺服務類別等。
  - **營運關聯完整性**：如趟次未指派司機、車輛資料未綁定、未回報之異常搭乘等。
  - **邏輯衝突檢驗**：如同一趟次兩台車重複回報有搭乘且未裁決等。

### 2.2 缺漏與異常視覺化標示
- 匯出彈窗或預覽介面中，檢核結果不得僅給出「有錯誤」的模糊文字，必須明確以表格或卡片列出：
  1. **問題資料識別**：個案姓名、服務日期、車牌號碼或趟次序號。
  2. **缺漏/異常欄位**：精確指出缺少哪一個欄位（例如：`身分證字號 (nationalId)`、`服務類別 (serviceCategory)`）。
  3. **問題說明**：以繁體中文說明缺失原因（例如：「個案未填寫戶籍地址，政府申報第 8 欄將留白」）。

### 2.3 雙軌快捷修正入口（Quick Fix Ingress）
在匯出預覽介面中，針對每一筆有缺漏的資料，系統必須提供以下兩種修復方式之一或兩者並行：
1. **快速跳轉連結**：
   - 於異常列提供「檢視／編輯個案」按鈕或超連結，點擊後在新分頁（或保留當前狀態下）開啟該實體的編輯頁面，方便使用者立即補正。
2. **原地即時設定（In-place Fix）**：
   - 在匯出對話框中直接提供輸入框或下拉選單，允許使用者原地設定補齊缺漏值（如快速補登司機、選擇服務類別），確認後立即更新該筆資料並重新檢核。

### 2.4 核心鐵律：非阻擋原則（Non-blocking Export）
- **絕對禁止阻礙匯出**：
  - 前置檢核的本質是「品質提示（Warning / Advisory）」，**不得作為阻擋匯出的硬性關卡**。
  - 即使資料存在缺漏或衝突，匯出畫面的「確認匯出」按鈕仍必須保持可用（Enabled）。
- **使用者自主決策權**：
  - 介面提供明確按鈕（例如：「忽略提示，直接依照現況完整匯出」）。
  - 使用者點選後，系統必須立即產出檔案，缺漏之欄位依各報表規格以空白留白或現有預設值產出，嚴禁跳出禁止匯出的阻斷性錯誤視窗。

## 準則三：資料匯入規範（比照匯出檢核、預覽與非阻擋處置）

批次匯入（如司機接送匯報 Excel、個案批次匯入檔）流程與互動邏輯，全面比照匯出檢核機制辦理。

### 3.1 匯入預覽與前置檢核機制
1. **上傳解析階段**：
   - 使用者上傳 `.xlsx` 檔案後，後端與前端首先進行檔案結構解析與欄位對應（Mapping）。
   - 系統不得在尚未向使用者展示檢核結果前，就暗中直接將資料全部硬寫入正式庫。
2. **全列資料檢核與問題標示**：
   - 系統依序比對每列資料：檢查格式（日期、身分證）、外鍵關聯（司機是否存在、單位是否存在）、必填欄位。
   - 匯入預覽表格中，將含有缺漏或格式異常的儲存格以醒目色彩（如橘色警告標籤、紅色底線）標記，並滑鼠懸停（Tooltip）或展開顯示明確原因。

### 3.2 就地修正與容錯處置
- **就地修改**：預覽介面應支援就地修正單筆資料欄位（或重新上傳覆蓋單一列），使用者修正後即時重新計算通過狀態。
- **非阻擋原則延伸**：
  - 遇到部分列資料有瑕疵時，系統不得直接中斷並拋棄整份檔案。
  - 使用者可選擇「匯入已驗證正確之資料，其餘問題資料依準則四轉入待維護」，確保業務日常匯入操作不因單筆髒資料而全盤停擺。

## 準則四：待維護資料機制（嚴格全站隔離與維護生命週期）

在匯入或資料建立過程中，若遭遇關鍵必填欄位缺失、或無效之外鍵關聯無法自動匹配時，啟動「待維護（Pending Maintenance）」機制。

```
[外部 Excel 匯入 / 系統建立]
           │
           ▼
   [資料完整性檢核]
      ├── 欄位完整且關聯正確 ────► [正式主檔資料庫] ──► 全站模組正常顯示與運作
      │
      └── 必填缺漏 / 關聯不存在
                 │
                 ▼
          寫入 [待維護區] (is_pending = true)
                 │
      ┌──────────┴──────────┐
      ▼                     ▼
[全站嚴格隔離隱藏]       [專屬待維護清單工作台]
• 排班日曆 ❌              │
• 司機派車 ❌              ├─► 【補齊必填/關聯】 ──► 驗證通過 ──► 解除待維護，全站顯示
• 趟次月結 ❌              │
• 政府申報 ❌              └─► 【忽略此筆】 ─────► 直接自系統移除 (硬刪除)
• 主檔清單 ❌
```

### 4.1 進入待維護的判定條件
1. **必填欄位缺失**：如個案未填寫姓名、身分證字號或格式嚴重錯誤（`profile_pending`）。
2. **關聯未建立或匹配失敗**：
   - 如司機接送匯報中填寫之司機姓名比對不到司機主檔（`driver_id IS NULL`）。
   - 個案指定之服務單位或去/回程車輛找不到對應主檔（`link_pending`）。
   - 照服員姓名或類型未填寫（`caregivers.is_pending`）。

### 4.2 核心鐵律：全站嚴格隔離（Strict Full-Site Isolation）
- **隔離範圍**：
  - 待維護狀態的資料，**絕對不得在待維護專區以外的任何地方顯示、選取或參與計算**！
  - 受隔離之業務端點與畫面包括但不限於：
    - 個案主檔正常列表（`GET /cases` 預設排除 `is_pending`）。
    - 排班日曆檢視與趟次生成。
    - 司機每日接送時刻表與班表。
    - 月結報表與儀表板在案數統計。
    - 政府申報匯出（申報資料不得包含待維護個案及其搭乘紀錄）。
- **底層強制保證**：
  - 資料庫層級透過統一 View（如 `case_pending_status`）或專屬狀態欄位進行標記。
  - 所有業務查詢一律透過 JOIN 該 View 並預設加上過濾條件，不可依賴前端自行隱藏。

### 4.3 待維護資料的生命週期與出口
待維護資料僅存在兩個合法出口，不允許長期處於不可維護的灰階狀態：
1. **補齊維護並轉正（Resolve & Clear）**：
   - 使用者在「待維護工作台」或指定待維護列表檢視該筆資料。
   - 使用者將缺漏之必填欄位補齊，或手動綁定正確的關聯實體（如手動指定對應之司機或單位）。
   - 儲存後，系統重新驗證；驗證通過後自動將 `is_pending` 清除，從待維護列表中移除，正式進入系統全站可用清單。
2. **忽略此筆＝從系統移除（Discard / Delete）**：
   - 若使用者判定該筆資料為無效資料、垃圾資料或錯誤重複匯入，可點選「忽略此筆」。
   - **語意與行為**：「忽略此筆」等同於直接從資料庫安全刪除該暫存記錄，不得使用假性標記（如 `ignored` 狀態）殘留於資料庫中。

## 準則五：前端錯誤處理與使用者體驗規範（嚴禁技術細節外露、統一錯誤代碼）

前端系統面向非技術背景的行政與長照作業人員，錯誤回饋必須以「友善、易懂、具指引性」為最高原則，同時提供明確索引以利工程維護。

### 5.1 嚴禁技術細節外露（Zero Technical Leaks）
- **禁止輸出內容**：
  - 前端所有 UI 元件（包括表單錯誤紅字、Toast 彈窗 `ElMessage`、通知條 `ElNotification`、確認對話框 `ElMessageBox`）嚴格禁止出現以下內容：
    - 資料庫原始錯誤（如 `pq: duplicate key...`、`violates foreign key`、`column does not exist`）。
    - 後端程式堆疊與系統內部字眼（如 `panic: runtime error`、`gin/recovery`、`nil pointer dereference`、`500 Internal Server Error`）。
    - 網路或協定層原始錯誤（如 `AxiosError: Request failed with status code 400`、`JSON.parse error`）。
- **轉譯要求**：
  - 任何底層錯誤在抵達使用者介面時，均必須經由前端攔截器與錯誤轉譯模組（`errorCodes.ts` / `resolveApiErrorMessage`）進行全面過濾。

### 5.2 使用者視角友善提示（User-Centric Messages）
- 錯誤訊息必須站在「長照業務使用者」的角度撰寫，清楚告知：
  1. **到底發生了什麼問題**（避免使用「資料庫約束衝突」，改用「身分證字號已存在於其他個案」）。
  2. **使用者當下該怎麼做**（具備指引性，如「請檢查輸入的身分證字號，或改用搜尋尋找既有個案」）。

### 5.3 結構化錯誤代碼機制（Standardized Error Codes）
- **錯誤代碼規範**：
  - 每個錯誤情境必須具備全系統唯一且具語意的全大寫代碼（例如：`VALIDATION_FAILED`、`CASE_NOT_FOUND`、`ASSIGNMENT_OVERLAP`、`IMPORT_TEMPLATE_MISMATCH`）。
- **前端顯示格式標準**：
  - 前端彈出錯誤訊息時，統一呈現格式：
    ```text
    [錯誤代碼] 友善中文提示訊息
    ```
    *範例：* `[ASSIGNMENT_OVERLAP] 該時段司機已有其他排班，請調整服務時間後再試。`
  - 若有複數欄位錯誤，則以條列方式呈現各欄位名稱與對應說明。
- **雙向效益**：
  - **使用者端**：回報問題時只需提供該代碼與畫面截圖，不必複製長串技術紀錄。
  - **開發人員端**：開發人員與運維工程師依錯誤代碼可直接全域搜尋程式碼與伺服器日誌（Audit Log / Server Log），在數秒內定位具體 Handler 與問題根因。

## 準則六：前後端協同變更與契約同步規範（規格同步、防範脫鉤）

本專案採前後端分離架構（Go Gin API + Vue 3 SPA）。任何一端的規格變動若未同步推進，將直接造成生產環境嚴重故障。

### 6.1 雙向同步審查原則（Bi-directional Synchronization）
- **修改後端時**：
  - 必須同步確認：前端是否有對應的 API Client 呼叫、DTO 型別定義、畫面表單控制項或錯誤處理。
  - 若後端新增、重命名、刪除欄位，或修改資料格式（例如：日期由 RFC3339 改為 `YYYY-MM-DD`、錯誤代碼新增），**必須在同一次任務中同步修改前端對應代碼**。
- **修改前端時**：
  - 必須同步確認：後端 Handler、Service 與 SQL Repository 是否支援前端送出的 Request Payload。
  - 禁止前端單方面自行假設後端支援新欄位或新篩選參數，造成 Silent Failure（靜默忽視）。

### 6.2 整合契約檢核項目（Contract Checklist）
在提交任何前後端修改前，必須依序核對以下四項整合點：
1. **API 路由與方法**：路徑（Path）、HTTP Method、URL Query 參數命名是否一致。
2. **DTO 與型別同步**：
   - 後端 `transport/*_dto.go` 與前端 `src/types/api.d.ts`（或 `src/api/*.ts`）是否完全對齊。
   - 資料庫為 `NULL` 的欄位在前端型別中是否標記為可選（`optional` / `null`）。
3. **權限矩陣同步**：
   - 後端路由掛載之 `middleware.RequirePermission(module, action)`，必須與前端路由表 `meta.module` 及前端 `hasPermission(module, action)` 保持 100% 同步。
   - 嚴防「前端畫面上看到按鈕，點擊後卻收到後端 403 FORBIDDEN」或「後端 API 已開放但前端選單被隱藏」的脫鉤現象。
4. **錯誤代碼一致性**：
   - 後端新引進的錯誤碼（`internal/platform/httpx/response.go`），必須同步登記至前端 `src/api/errorCodes.ts` 的 `API_ERROR_MESSAGES` 對照表，並撰寫對應的單元測試。

## 準則七：前端操作情境 E2E 測試規範（模擬真實操作、流程完整覆蓋）

為確保使用者所有日常操作流程在版本迭代中維持零迴歸（No Regression），所有前端功能均必須具備對應之端到端（End-to-End, E2E）自動化測試。

### 7.1 測試定位與核心精神
- **真實模擬使用者情境**：
  - 測試必須模擬真實使用者的瀏覽器行為：填寫表單、點擊按鈕、切換分頁、上傳檔案、下載匯出、關閉彈窗。
  - 不得僅測試靜態 DOM 是否渲染，必須驗證完整的使用者操作閉環（Operation Flow Closed-loop）。
- **真實環境對齊**：
  - E2E 測試環境必須打真實 API 與本機 PostgreSQL 資料庫，嚴禁使用 MSW 假資料或攔截假 Session，確保測試結果反映真實系統行為。

### 7.2 必須涵蓋的四大情境覆蓋率
每一個前端功能模組上線前，E2E 測試套件必須涵蓋以下情境：
1. **正常操作流程（Happy Path）**：
   - 新增主檔 ➔ 列表即時呈現 ➔ 編輯欄位 ➔ 儲存後數值更新 ➔ 啟用/停用狀態切換生效。
2. **匯出前置檢核與非阻擋流程（Export Flow）**：
   - 觸發匯出 ➔ 檢核視窗正確標示缺漏個案與缺漏欄位 ➔ 測試快捷跳轉/就地修正 ➔ 點選「非阻擋直接匯出」 ➔ 驗證瀏覽器成功接收檔案下載。
3. **匯入與待維護隔離流程（Import & Pending Flow）**：
   - 上傳含有缺少必填欄位的 Excel 檔 ➔ 驗證資料被標記並寫入待維護區 ➔ 驗證排班日曆與主檔正常列表**完全查不到該筆資料** ➔ 進入待維護工作台完成補齊維護 ➔ 驗證該筆資料正式於常規列表與日曆中現身。
4. **異常處理與錯誤碼顯示（Error Handling Path）**：
   - 輸入故意重複的身分證字號或錯誤日期格式 ➔ 驗證畫面彈出非技術性的白話錯誤提示 ➔ 驗證錯誤代碼（如 `[VALIDATION_FAILED]`）明確呈現在介面上。

### 7.3 測試執行紀律與維護規範
- **測試資料獨立性（Test Isolation）**：
  - 測試案例所需之資料應盡可能由測試前置流程建立（或由明確的本機種子腳本產出），避免硬編碼假資料姓名或相依前次測試殘留的髒資料。
- **測試執行原則**：
  - 平常本機快速開發時，以 `npm run type-check`、`npm run build` 與單元測試為主，避免無差別耗時執行全量 E2E。
  - 但在完成功能特性（Feature）、改版交付或執行完整系統驗收時，必須運行對應之 Playwright E2E 測試，確保所有前端使用者操作情境皆 100% 正確運作。
