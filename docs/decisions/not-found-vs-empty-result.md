# 查無資料：primary resource 404 vs. 衍生查詢 200+null

## Context

`apps/web/src/api/client.ts` 的全域回應攔截器對所有非 401／403 錯誤一律跳出
`ElMessage.error(...)` 提示。`GET /cases/:id/schedule`（個案現行排班）過去在
查無現行排班時回傳 `404`／`CodeNotFound`，即使前端呼叫端已用 `.catch()` 把它
當成合法的「尚無排班」狀態處理，全域攔截器仍搶先跳出「查無資料」提示——
因為攔截器在呼叫端的 `.catch()` 執行之前就已經對這個 HTTP 狀態碼做出反應。

問題根源不在攔截器，而在於這個端點把兩種不同語意的「查無資料」混用同一個
狀態碼：「個案尚無現行排班」是查詢條件下的合法空結果，不是需要提醒使用者
的錯誤，卻用了通常代表「這個資源不存在」的 `404`。

## Decision

判斷依據是 API 語意，不是「DB 查不到就一律 404」。依端點形狀分三種：

| 端點形狀 | 範例 | 查無資料時 |
| --- | --- | --- |
| 單一資源，該資源本應存在 | `GET/PUT/PATCH/DELETE /cases/:id`、`/sites/:id`、`/rides/:id` | `404`／`CodeNotFound` |
| 集合／清單／搜尋結果 | `GET /cases`、`GET /cases?q=王` | `200` + 空陣列 |
| 子資源或欄位可以不存在 | `GET /cases/:id/schedule` | `200` + `data: null` |

```text
GET /cases/:id            指定某一筆，找不到 → 404
GET /cases?q=王          查詢集合，找不到 → 200 + []
GET /cases/:id/schedule   個案的衍生狀態，可以不存在 → 200 + data: null
```

第三種最容易混淆，判斷依據是：這個子路徑在 domain 裡算不算「獨立資源」。
算獨立資源（例如刪除它、對它單獨定版本，是有意義的操作）就回 `404`；只是
父資源上「可能還沒有值」的衍生狀態或 optional 欄位（例如「這個個案目前生效
中的排班」——排班存在與否會隨日期變化，不是一個可以獨立被刪除或定版的東西）
就回 `200` + `null`。

查無資料回 `404` 的核心判準是「使用者需要被告知你指定的這個東西不存在／有
問題」；集合 0 筆或衍生狀態不存在，對使用者來說都是正常的查詢結果，不該與
真正的錯誤共用同一個狀態碼。

## Alternatives

- **前端加旗標略過全域提示**（例如替個別請求加
  `{ skipErrorToast: true }`）：曾短暫採用又撤回。缺點是治標不治本——後端
  契約仍把合法空結果包裝成錯誤狀態碼，往後每個呼叫端都要自行記得比對「這個
  404 到底是不是要顯示」，且無法從 HTTP 狀態碼本身看出這個端點的真實語意。
- **維持全部查詢一律 404**：符合部分 REST 慣例，但會讓「合法空結果」與
  「真正的錯誤」共用同一個全域錯誤提示路徑，任何呼叫端想優雅處理空結果都要
  額外寫 `.catch()` 攔截特定狀態碼，且容易在攔截器層級被搶先跳出提示（如本
  次事故）。

## Consequences

- 新增或修改端點時，先判斷是「單一資源」「集合／搜尋」還是「可以不存在的子
  資源／欄位」，據此決定 `404`、`200+[]` 或 `200+null`，不要憑直覺或抄鄰近
  端點。
- 前端呼叫端可以直接把回應資料的 `null` 或空陣列當成正常空狀態渲染，不需要
  為這類查詢額外寫錯誤攔截邏輯，也不需要在 `apiClient` 層級提供略過全域提示
  的旗標。
- 現有的單一資源 lookup／mutation（`cases/:id`、`sites/:id`、
  `drivers/:id`、`rides/:id` 等 GET／PUT／PATCH／DELETE）查無資料時繼續回
  `404`，不受本決策影響；清單類端點（如 `GET /cases`）本來就已經是 0 筆回
  `200+[]`，同樣不受影響。
