## 0. 使用方式

1. 本文件與文件 01–08 衝突時，**以本文件為準**；文件 03 需修訂之處已列於 §12.1。
2. 規格中標示 **`【待確認】`** 者尚未定案，實作時**不得自行決定**，需先取得答覆並回填本文件。

## 2. 共通約定

### 2.1 資料格式

| 型別 | 格式 | 範例 | 說明 |
|---|---|---|---|
| 日期 | `YYYY-MM-DD` | `2026-07-01` | 西元，API 一律用此格式 |
| 時間 | `HH:mm` | `09:40` | 24 小時制，補零 |
| 時間戳記 | RFC 3339（UTC） | `2026-07-01T05:10:42Z` | 前端負責轉台北時間顯示 |
| 民國年月（API） | `RRR-MM` | `115-07` | query 參數 `month` |
| 民國年月（DB） | `CHAR(5)` | `11507` | `export_jobs.period_ym` |
| 民國日期（申報用） | 7 碼整數 | `1150701` | 僅出現在匯出檔內 |
| 金額／單價 | 數值，小數 2 位 | `115.00` | 不用字串 |
| 里程 | 數值，小數 2 位 | `5.00` | |
| 身分證（一般回應） | 遮罩字串 | `A20***9750` | 見 §4.4 |

**JSON 欄位一律 camelCase**（`caseId`、`serviceDate`、`tripPattern`），資料庫一律 snake_case，轉換在 repository 層完成。

### 2.2 清單端點的共通參數

所有 `GET` 清單端點支援：

| 參數 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `page` | int | `1` | 從 1 起算 |
| `pageSize` | int | `20` | 上限 `100`，超過回 400 |
| `sort` | string | 各端點自訂 | 格式 `field` 或 `-field`（減號為降冪） |
| `q` | string | — | 關鍵字，比對範圍各端點自訂 |

回應：

```jsonc
{ "data": [ /* ... */ ],
  "meta": { "page": 1, "pageSize": 20, "total": 235, "totalPages": 12 } }
```

### 2.3 錯誤碼

失敗一律回：

```jsonc
{ "error": { "code": "VALIDATION_FAILED",
             "message": "里程數必須大於 0",
             "details": [ { "field": "distanceKm", "reason": "必須大於 0" } ] } }
```

**前端依 `code` 分支，不解析 `message` 文字。**

| `code` | HTTP | 意義 | 前端處理 |
|---|---|---|---|
| `VALIDATION_FAILED` | 400 | 欄位驗證失敗 | 標註 `details[].field` 對應的表單欄位 |
| `UNAUTHENTICATED` | 401 | 無 Token 或已過期 | 更新 Token 一次，仍失敗則導回登入 |
| `FORBIDDEN` | 403 | 角色權限不足 | 顯示「權限不足」，不導頁 |
| `NOT_FOUND` | 404 | 資源不存在 | 顯示空狀態 |
| `DUPLICATE_NATIONAL_ID` | 409 | 身分證重複 | 標註身分證欄位 |
| `ASSIGNMENT_OVERLAP` | 409 | 司機車輛期間重疊 | 標註期間欄位 |
| `EXPORT_IN_PROGRESS` | 409 | 同範圍已有進行中的匯出 | 導向該工作的進度 |
| `PRECHECK_FAILED` | 422 | 前置檢核有 error | 展開 `details` 列出問題個案 |
| `MAPPING_REQUIRED` | 422 | 尚有待對應欄位 | 導向 `/forms/mappings` |
| `INGEST_TOKEN_INVALID` | 401 | webhook 密鑰錯誤 | 不適用（非前端） |
| `INTERNAL_ERROR` | 500 | 未預期錯誤 | 顯示通用訊息，同時送 Sentry |

### 2.5 稽核寫入時機

以下動作**必須**寫 `audit_log`，缺一即為缺陷：

| `action` | 觸發時機 | `before` / `after` |

| `claimEndDate` | — | 若有值需 ≥ `claimStartDate` |

### 3.2 排班設定 `case_schedules` / `schedule_legs`

| 欄位 | 必填 | 規則 |
|---|:---:|---|
| `siteId` | ✓ | 需存在且 `region` 與個案一致，否則回 `VALIDATION_FAILED` |
| `effectiveFrom` | ✓ | 同一個案的有效期間不得重疊 |
| `weekdays` | ✓ | 1–7 的陣列，至少 1 個，不重複 |
| `tripPattern` | ✓ | `1` / `2` / `4` |
| `unitPrice` | ✓ | > 0，≤ 9999.99，預設 115 |
| `distanceKm` | ✓ | > 0，≤ 999.99，**無預設值** |
| `serviceDurationMin` | ✓ | 1–240，預設 10 |
| `serviceCode` | ✓ | 預設 `BD03` |
| legs 數量 | ✓ | 需等於 `tripPattern`（1 → 1 筆、2 → 2 筆、4 → 4 筆） |
| legs 方向組合 | ✓ | `2` 趟必為 `outbound` + `inbound`；`4` 趟必為 `out/in/out/in`（leg_seq 1–4） |

### 3.4 身分證檢查碼演算法

```
字母對照：A=10 B=11 C=12 D=13 E=14 F=15 G=16 H=17 I=34 J=18 K=19 L=20
          M=21 N=22 O=35 P=23 Q=24 R=25 S=26 T=27 U=28 V=29 W=32 X=30 Y=31 Z=33

n  = 字母對照值           # 兩位數 n1 n2
sum = n1 + n2*9
      + d1*8 + d2*7 + d3*6 + d4*5 + d5*4 + d6*3 + d7*2 + d8*1
      + d9                  # d9 為檢查碼
合法條件：sum % 10 == 0
```

第 2 碼（性別碼）接受 `1`、`2`、`8`、`9`（後兩者為新式外來人口統一證號）。

## 4. 核心演算法規格

每條規則只有一個實作位置（文件 08 §5）。以下規定輸入、輸出與必須通過的邊界案例。

### 4.1 民國日期（R2）— `domain/rocdate`

```
ToROC(d time.Time) int          // 2026-07-01 → 1150701
FromROC(v int) (time.Time, error)
```

- 民國年 = 西元年 − 1911，格式化為 3 碼（不足補零）；月、日各 2 碼補零。
- **禁止字串拼接**，一律走此函式。
- 必測案例：

| 輸入 | 輸出 | 說明 |
|---|---|---|
| `2026-07-01` | `1150701` | 一般 |
| `2026-01-01` | `1150101` | 年初 |
| `2026-12-31` | `1151231` | 年末 |
| `2028-02-29` | `1170229` | 閏年 |
| `1912-01-01` | `0010101` | 民國元年，年份補零 |
| `1911-12-31` | error | 早於民國元年 |

### 4.2 服務時段（R3）— `domain/timeslot`

```
EndTime(depart time.Time, durationMin int) (hour, minute int)
```

- 結束時間 = 起始 + `serviceDurationMin`，回傳拆開的時、分。
- 跨小時進位由此函式處理；**跨日（超過 23:59）視為設定錯誤，回 error**。
- 必測案例：

| 起始 | 時長 | 結束時 | 結束分 |
|---|---|---|---|
| 09:40 | 10 | 9 | 50 |
| 09:55 | 10 | 10 | 5 |
| 09:00 | 60 | 10 | 0 |
| 23:55 | 10 | — | error |

### 4.3 姓名與地址正規化 — `domain/namenorm`

```
Normalize(s string) string        // 供比對用，不改寫原始資料
```

處理順序（**順序不可調換**）：

1. Unicode **NFKC** 正規化 —— 全形數字轉半形（樣本地址含 `２６４號`）、全形括號轉半形。
2. 移除所有空白字元（半形空格、全形空格、tab）—— 樣本有 `3.鄧甜妹  [去程]` 雙空格。
3. 異體字映射表 —— 至少涵蓋 `温→溫`、`裡→裏`、`著→着` 等；映射表放 `domain/namenorm/variants.go`，可增補。
4. 轉小寫（僅影響英數）。

**原始欄位（`name`、`home_address`）永遠保存未正規化的原文**，正規化結果另存 `name_normalized`。罕用字（`𣵛`、U+23D5B，屬 CJK 擴充 B 區）為 4 位元組 UTF-8，**測試需明確涵蓋**。

欄名解析另有專用函式（§5.4），不與此函式混用。

### 4.4 身分證加密與遮罩 — `domain/crypto`

| 函式 | 規格 |
|---|---|
| `Encrypt(plain) []byte` | AES-256-GCM，隨機 12 位元組 nonce，輸出 `nonce ‖ ciphertext ‖ tag`。同一輸入每次密文不同 |
| `Decrypt(cipher) string` | 驗證失敗回 error，**不得回空字串矇混** |
| `Index(plain) []byte` | HMAC-SHA256(key, plain)，供唯一性檢查與精準查詢。同一輸入結果固定 |
| `Mask(plain) string` | 前 3 碼 + `***` + 後 4 碼，如 `A202559750` → `A20***9750`。長度不足 10 時全部遮罩 |

金鑰由環境變數提供（§10），加密金鑰與 HMAC 金鑰**必須不同**。

### 4.5 應搭乘日曆與趟數展開（R4／R6／R8）— `domain/calendar`

```
ExpectedRides(caseID, year, month) []ExpectedRide{Date, LegSeq}
```

計算步驟：

```
1. 取該月所有日期
2. ∩ 星期 ∈ case_schedules.weekdays
3. ∩ 星期 ∈ sites.open_days
4. ∩ date >= cases.claim_start_date            (R8)
5. ∩ date <= cases.claim_end_date（若有）
6. ∩ 排班設定的 effective_from / effective_to 區間內
7. − holidays 表中該月的國定假日與臨時停駛日
8. × 該排班的全部 schedule_legs（1、2 或 4 筆）
```

- 排班設定在該月**有空窗**（部分日期無任何有效排班）時，該區間不產生應搭日，並在檢核回報 error。
- `holidays` 資料表：

```sql
CREATE TABLE holidays (
  holiday_date DATE PRIMARY KEY,
  name         TEXT NOT NULL,
  region       TEXT,          -- NULL = 全區適用（如颱風假可只停單區）
  source       TEXT NOT NULL DEFAULT 'manual' CHECK (source IN ('gov_calendar','manual'))
);
```

### 4.6 合併（R5）— `domain/merge`

輸入：某個 `(caseId, serviceDate, legSeq)` 的全部 `ride_sources`（可能跨多台車、跨多筆回覆）。

```
1. 依 vehicle_id 分組
2. 每組取「所屬 form_submissions.submitted_at 最新」的一筆為該車的有效回報   ← 見 §12.1 D3
3. boarded = 各車有效回報中 reported='boarded' 的集合
4. mergedStatus = len(boarded) > 0 ? boarded
                : 有任何有效回報   ? absent
                :                    unreported
5. hasConflict = boarded 中相異 vehicle_id 數量 > 1
6. vehicle/driver：
     hasConflict 且已人工裁決 → 保留既有值，不覆寫
     已被人工更正             → 保留既有值，不覆寫
     否則 boarded 非空        → 取 boarded 中 submitted_at 最早者的車與司機
     否則                     → 取排班設定的預設車輛與其當日主要司機
7. effectiveStatus：
     已被人工更正（corrected_at 非空）→ 不動，並標記 sourceChanged = true 供畫面提示
     否則                              → = mergedStatus
```

**第 2 步與第 6、7 步的「不覆寫人工結果」是 AC-2 的明列條件。** 合併函式為純函式（輸入輸出皆為資料結構、不碰資料庫），必須以單元測試覆蓋下列情境：

| 情境 | 期望 |
|---|---|
| 單車回報有坐 | `boarded`，無衝突 |
| 單車回報沒坐 | `absent` |
| 無任何回報 | `unreported` |
| A 車沒坐、B 車有坐 | `boarded`，車輛取 B，無衝突 |
| A 車有坐、B 車有坐 | `boarded`，`hasConflict = true` |
| 同車先報有坐、後報沒坐 | `absent`（取最新） |
| 已裁決後重跑同步 | 車輛／司機維持人工指定值 |
| 已更正後來源改變 | `effectiveStatus` 不變，`sourceChanged = true` |

### 4.7 搭乘紀錄更正

司機在 Google 表單填錯、漏填或事後補報時，行政人員可直接更正搭乘紀錄。

> **這不是規則 R7 的「未搭乘仍申報」機制。** R7 已決議不實作（§12.2 Q9）：系統不提供以「產生與司機回報不符的申報資料」為目的的功能，也沒有 `allow_manual_override` 旗標與書面授權流程。本節是單純的資料更正，用途是修掉填寫錯誤。

**端點**：`PATCH /rides/{id}`，權限 `staff+`。

| 可更正欄位 | 說明 | 未更正時的取值 |
|---|---|---|
| `effectiveStatus` | 有坐／沒坐／未回報 | `merged_status` |
| `vehicleId` | 實際承載車輛 | 合併結果（混車裁決亦走此欄位） |
| `driverId` | 實際駕駛 | 合併結果 |
| `departTimeOverride` | 該筆的實際出發時間 | `schedule_legs.depart_time` |
| `durationMinOverride` | 該筆的實際服務時長 | `case_schedules.service_duration_min` |
| `legSeq` | 趟次（改到同日的其他時段） | 匯入時綁定的時段 |
| `notClaimedAa09` | 第 17 欄旗標 | `false` |
| `reason` | 更正原因，**選填** | — |

資料模型需補兩欄（文件 03 §2.4 之外的增補）：

```sql
ALTER TABLE ride_records
  ADD COLUMN depart_time_override  TIME,      -- NULL = 沿用 schedule_legs.depart_time
  ADD COLUMN duration_min_override SMALLINT,  -- NULL = 沿用 case_schedules.service_duration_min
  ADD COLUMN corrected_by          UUID,
  ADD COLUMN corrected_at          TIMESTAMPTZ,
  ADD COLUMN correction_reason     TEXT;      -- 選填
```

原文件 03 的 `override_reason` / `overridden_by` / `overridden_at` 三欄由上列 `correction_*` 欄位取代，語意更貼近實際用途。

**規則**：

1. `reason` **選填**，前端提供常用原因快選：`司機填錯`、`司機漏填`、`事後補報`、`混車確認`、`其他`。選了即帶入文字，也可自行輸入或留空。
2. 操作者、時間、**全部異動欄位的前後值**一律寫入 `audit_log(action='correct')`，這是稽核的真正依據，不依賴 `reason`。
3. 更正過的紀錄（`corrected_at` 非空）**不被後續的重新合併覆蓋**（§4.6 第 6、7 步）；來源資料事後改變時標記 `sourceChanged = true`，畫面提示「來源資料已變更，請重新確認」。
4. `legSeq` 更正需檢查同一 `(case_id, service_date, leg_seq)` 目標位置未被占用，衝突回 `409`。
5. `departTimeOverride` 與 `durationMinOverride` 會直接影響政府申報表第 8–11 欄。**前端須預帶排班設定的原值並顯示差異**，匯出前置檢核另列 warning（§7.6）。
6. 恢復預設：任一 override 欄位傳 `null` 即回復沿用排班設定值。

## 5. Google 表單匯入規格

> 本節內容為**實際解析 `竹北一車 (回覆).xlsx`（65 列 × 56 欄）與 `竹南2車 (回覆).xlsx`（108 列 × 62 欄）所得**，非推測。

### 5.1 工作表與欄位結構

- 工作表名稱：**`表單回覆 1`**（「覆」與「1」之間為半形空格）。
- 第 1 列為標題列，第 2 列起為資料。
- 固定前三欄：`時間戳記`、`今天日期`、`今日駕駛人`。
- 第 4 欄起為搭乘欄與 `問題回報` 欄，**`問題回報` 不一定在最後一欄**（竹北一車在第 40 欄、竹南 2 車在第 39 欄），必須依標題文字判斷，不可用位置。
- 尾端存在標題為空（`None`）的欄，**一律忽略**。

### 5.2 列的取捨規則

| 條件 | 處理 |
|---|---|
| `今天日期` 為空 | **整列跳過**。樣本最後一列是人工加的統計列（各欄為整數合計，前三欄皆空），不得寫入 |
| 整列皆空 | 跳過（竹南 2 車第 107 列） |
| `今天日期` 有值但 `今日駕駛人` 為空 | 寫入 `form_submissions`，`driver_id` 為 NULL，列入匯入異常 |
| `時間戳記` 早於 `今天日期` | 正常，不視為異常（司機常於隔日凌晨補報，樣本可見 03/04 01:07 回報 03/03） |

**服務日期一律取 `今天日期` 欄，不得使用 `時間戳記`。**

### 5.3 儲存格值判定

先做 `TrimSpace`（含全形空白）再判定：

| 值 | 判定 |
|---|---|
| `有坐` | `reported = boarded` |
| `沒坐` | `reported = absent` |
| 空字串 / `None` | 不產生 `ride_sources`（視為該日未涉及此欄） |
| 其他任何值 | **不猜測**：不產生 `ride_sources`，寫入匯入異常清單，`payload` 保留原值。樣本實例：`去程到07/21`（自由文字寫在搭乘欄）、整數值（統計列，已於 §5.2 濾除） |

`問題回報` 欄存入 `form_submissions.issue_text`；值為 `無` 時仍原樣保存，不轉為 NULL。

### 5.4 欄名解析與推薦

欄名樣態（樣本實例）：

```
1. 張詹竹妹 [去程]
2.曾細嬌 [去程] 2                              ← Google Sheets 對重複欄名自動加的 " 2" 後綴
3.鄧甜妹  [去程]                               ← 姓名後雙空格
1.吳𣵛桂(去程竹3) [去程]                        ← 罕用字 + 括號業務註記
1.陳素貞(4趟)*可能下午回竹1車載 [(早午)去程]      ← 星號註記 + 方向前綴
6.顏湯月淑 (改2趟) *可能下午回,竹1車載 [(早午)回程]
8.葉秀珍 (4趟) *早去午回竹3載;下午回竹1車載 [去程]
1.曾蕭碧雲(W1.5下午回程竹1車載) [第 3 列]         ← 方向標記異常，見下
```

解析步驟：

```
1. 取末尾方括號內容為「方向標記」：
      [去程] [(早午)去程]              → outbound
      [回程] [(早午)回程]              → inbound
      其他（如 [第 3 列]）             → 無法判定，kind='unknown'，進待對應佇列
2. 去除末尾的 " 2"、" 3" 等 Google 重複欄後綴
3. 去除開頭的「數字 + . 」序號
4. 去除所有括號內容：() （） 與其內容
5. 去除 * 之後的全部文字
6. 對剩餘字串套用 §4.3 的 Normalize()，得到候選姓名
7. 與 cases.name_normalized 比對：
      完全相等且唯一          → suggestion_score = 1.0
      完全相等但多筆          → 全部列為候選，score = 0.8，需人工選
      編輯距離 ≤ 1            → score = 0.6
      其餘                    → 無推薦
8. 一律寫入 form_columns(mapping_status='pending', suggested_case_id, suggestion_score)
```

**任何分數都不自動套用**（R3 對策、原則 B-3）。管理者確認後 `mapping_status` 轉 `mapped`，並觸發該表單歷史資料重新正規化。

序號重複（竹北一車同時有兩個 `10.`、兩個 `11.`）、同人多欄（`2.曾細嬌 [去程]` 與 `2.曾細嬌 [去程] 2`）皆為正常情形：**序號不參與比對**，同人多欄各自綁定、合併時自然 OR。

### 5.5 綁定與四趟展開

`form_columns` 綁定的是 **`(case_id, leg_seq)`**，資料表無 `direction` 欄位；方向由 `schedule_legs.leg_seq` 反查（§12.1 D2）。

| 個案 `tripPattern` | 表單欄方向 | 綁定 `leg_seq` | 寫入的 `ride_sources` |
|---|---|---|---|
| 1（單去） | outbound | 1 | leg 1 |
| 1（單回） | inbound | 1 | leg 1 |
| 2 | outbound | 1 | leg 1 |
| 2 | inbound | 2 | leg 2 |
| **4** | outbound | 1 | **leg 1 與 leg 3** |
| **4** | inbound | 2 | **leg 2 與 leg 4** |

四趟展開即規則 R4（逐字稿 30:00）：表單只有一組去／回程勾選，系統自動展開成四筆。

### 5.6 司機對應

1. 取 `今日駕駛人` 字串，套用 §4.3 `Normalize()`。
2. 與 `drivers.name_normalized` 比對：唯一相符 → 綁定 `driver_id`。
3. 不相符或多筆相符 → `driver_id` 為 NULL，寫入匯入異常清單，**不猜測**。
4. 匯出時第 7 欄若 `ride_records.driver_id` 為 NULL，退回 `driver_assignments` 該日的主要司機；仍無則檢核回 error。

### 5.7 webhook 與對帳軌

| 項目 | 規格 |
|---|---|
| 端點 | `POST /api/v1/ingest/google-form` |
| 驗證 | `X-Ingest-Token`，每份表單一組，比對 `google_forms.ingest_secret_ref` 指向的密鑰；失敗回 401 `INGEST_TOKEN_INVALID` |

## 6. 批次匯入規格

三種批次匯入一律**兩段式**：`POST .../import?dryRun=true` 回傳預覽與逐列問題 → 管理者確認 → `dryRun=false` 寫入。

### 6.1 個案（`個案新增資料.xlsx`）

實測結構：工作表名為月份（`7月`、`8月`），**第 1 列為大標（如 `7月新增個案`），第 2 列才是標題列，第 3 列起為資料**。

| 來源欄 | 目標 | 轉換規則 |
|---|---|---|
| 序號 | — | 忽略 |
| 姓名 | `cases.name` | 值以 `例:` 開頭者為範例列，**整列跳過**（樣本第 3 列為 `例:王小明`） |
| 申報地區 | `cases.region` | `苗栗`→`miaoli`、`新竹`→`hsinchu`，其他值報錯 |
| 幾號開始申報 | `cases.claim_start_date` | 來源為 datetime，取日期部分 |
| 據點 | `case_schedules.site_id` | 依名稱比對 `sites`，比對不到報錯（不自動建立據點） |
| 每週據點開放時間 | `case_schedules.weekdays` | 自由文字，見 §6.2 |
| 去程時間 | leg（outbound）`depart_time` | 來源為 time；**為空代表無去程** |
| 回程時間 | leg（inbound）`depart_time` | 同上 |
| 去程車名／回程車名 | leg `vehicle_id` | 依 `vehicles.display_name` 比對，比對不到報錯 |
| 備註 | `case_schedules.note` | 原樣保存 |

`tripPattern` 由去／回程時間推導：兩者皆有 → `2`；僅一者 → `1`。**四趟個案無法由此檔判斷**，需匯入後人工改為 `4` 並補四段時間（客戶協作事項 2）。

匯入時缺漏欄位的處理：

| 欄位 | 缺值處理 |
|---|---|
| `nationalId`、`homeAddress`、`serviceUsageType` | 來源檔沒有這些欄 → 建立為**草稿個案**（`status='suspended'`），列於「待補資料」清單；補齊前不得匯出 |
| `distanceKm` | 無預設值 → **該列標為 error，不可寫入** |
| `unitPrice` | 帶預設 115，預覽標示「使用預設值，請確認」（黃色） |
| `serviceDurationMin` | 帶預設 10，同上 |

### 6.2 「每週據點開放時間」解析

自由文字，實測值：`週一到週五`、`週四、週五`、`週二，週四下午去回`、`周一早上來回`（`周`／`週` 混用）。

```
1. NFKC 正規化，移除空白
2. 「周」統一轉「週」
3. 抽出全部「週X」出現的位置：一=1 二=2 三=3 四=4 五=5 六=6 日/天=7
4. 若含「到」或「~」或「-」，取兩端展開為連續區間（週一到週五 → 1,2,3,4,5）
5. 其餘以「、」「，」「,」分隔，逐一取值
6. 「早上」「下午」「來回」「去回」等詞彙**不參與 weekdays 計算**，原樣保留於 note 供人工參考
7. 解析結果為空 → 該列標為 error，需人工填寫
```

**解析結果一律在預覽中顯示為可修改的星期複選框**，人工確認後才寫入 —— 這是自由文字欄位唯一安全的處理方式。

### 6.3 據點與司機（`(參考用)交通車接送班表.xlsx`）

**據點** —— `據點` 工作表，第 1 列為標題 `車次｜據點｜地址`，第 2 列起為資料（實測 11 筆有效列，`max_row` 為 1003 但多為空列，**須以第 1 欄有值為有效列判準**）。

| 來源欄 | 目標 |
|---|---|
| 車次 | 比對 `vehicles.display_name`，建立據點與車輛的參考關聯 |
| 據點 | `sites.name` |
| 地址 | `sites.address` |

**司機** —— `11507接送時間表` 工作表，A 欄的區塊標題格式為 `湖口(郭澤威 G121806465)`：

```
正則：^(?P<site>.+?)\((?P<name>\S+)\s+(?P<nid>[A-Z][0-9]{9})\)$
→ drivers.name = 郭澤威、drivers.national_id = G121806465、預設車輛 = 依 site 對應
```

比對不到車輛或身分證檢查碼不合法者列為 error，不寫入。

- **第 25／26 欄（R1）**：`outbound` → 出發地＝`cases.home_address`、目的地＝`sites.address`；`inbound` 兩者對調。樣本第 20 列（0-based）起出發地變為據點地址，即去回程交界。
- **第 7 欄**：`ride_records.driver_id` 為 NULL 時退回 `driver_assignments` 該日主要司機；仍無 → 檢核 error。
- **第 10／11 欄**：`depart_time + case_schedules.service_duration_min`，走 §4.2 函式。

### 7.5 列的產生與排序

**只輸出 `effective_status = 'boarded'` 的搭乘紀錄**，一筆 `ride_records` 產生一列。

排序規則（樣本實測）：

```
1. 先輸出全部去程（leg 方向為 outbound），依服務日期升冪
2. 再輸出全部回程（inbound），依服務日期升冪
3. 四趟個案：leg1 全月 → leg2 全月 → leg3 全月 → leg4 全月
4. 單檔多案模式：先依身分證字號排序，同一個案內再套用上述規則
```

> **去程與回程的日期清單各自獨立**：樣本中去程 19 筆（07/01–07/29）、回程 20 筆（07/01–07/30），兩者天數不同。**不可假設去回程成對**，也不可用「總筆數 ÷ 2」推算。

### 7.6 前置檢核

匯出前一律先跑，結果寫入 `export_jobs.precheck`。**有任何 error 即擋下匯出並回 `PRECHECK_FAILED`。**

| 等級 | 檢查項 | `details` 內容 |
|---|---|---|
| error | 個案缺身分證／住家地址／服務使用類型 | `caseId`、`caseName`、`field` |
| error | 排班設定缺里程 | 同上 |
| error | 當日司機無身分證資料 | `caseId`、`serviceDate` |
| error | 排班設定在申報月份內不存在或有空窗 | `caseId`、缺漏日期區間 |
| warning | 混車衝突未處理（`has_conflict` 且未裁決） | `rideId`、涉及車輛清單 |
| warning | 應搭日但狀態為 `unreported` | `caseId`、日期清單 |
| warning | 當月零趟數 | `caseId` |
| warning | 有紀錄的出發時間或服務時長與排班設定不符（§4.7 更正） | `rideId`、排班值與實際值 |
| info | 本月有更正紀錄 N 筆 | 明細清單（含更正原因，未填則顯示「未填寫」） |
| info | 個案配給額度檢查**未執行**（規則未提供） | 固定文字，見下 |

**warning 與 info 不阻擋匯出**，但必須在畫面完整列出。

> **配給額度檢核（Q7 決議）**：客戶尚未提供長照給付額度計算基準，此項**保留入口但不執行檢查**。檢核結果固定回傳一筆 info：「個案配給額度檢查未執行——尚未取得額度計算規則」。目的是讓客戶在畫面上看得見這個缺口，而不是讓它悄悄消失。規則到位後只需補上計算，前端不需改動。

## 8. 其他報表輸出規格

### 8.1 車輛趟數表（F5）

格式不拘（客戶：內部看得懂就好）。規定最低內容：列＝個案、欄＝`去程趟數｜回程趟數｜合計`，依車輛分工作表，末列為該車合計。同時提供網頁檢視與 `.xlsx` 匯出。

### 8.2 新竹接送時刻表（F6）

依 `(參考用)交通車接送班表.xlsx` 的 `竹北` 工作表格式（實測）：

- 第 1 列留空，第 2 列為標題：`去程 | (空) | 姓名 | (備註) | 出發時間 | 出發地 | 抵達時間 | 目的地`。
- 第 2 欄為趟次（`第一趟`、`第二趟`…），**僅在該趟第一列出現，其餘列留空**。
- 去程區塊結束後另起回程區塊，格式相同。
- 排序：`direction` → `run_no` → `depart_time`。
- 資料來源為 `schedule_legs`（排班設定），**非實際搭乘紀錄**。
- 輸出 `.xlsx`，並提供 A4 橫式列印樣式。

### 8.3 空白維修保養表（F8）

系統產生空白表格供人工填寫（客戶明確要求）。欄位：`日期｜車號｜里程數｜保養項目｜廠商｜金額｜備註｜簽名`，每車一張，含表頭與 12 列空白列。

### 8.4 通知收件人管理（Q8 決議）

F4 未回報通知與 F10 請假通知的收件人由資料表管理，可依通知類型指定不同對象，**不使用環境變數**。

```sql
CREATE TABLE notification_recipients (
  id         BIGSERIAL PRIMARY KEY,
  topic      TEXT NOT NULL CHECK (topic IN ('missing_report','driver_leave','month_end','export_failed')),
  email      TEXT NOT NULL,
  display_name TEXT,
  active     BOOLEAN NOT NULL DEFAULT true,
  created_by UUID NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (topic, email)
);
```

| 項目 | 規格 |
|---|---|
| 管理頁 | `/settings/notifications`，權限 **admin**；`staff` 與 `viewer` 唯讀 |
| API | `GET/POST/PATCH/DELETE /settings/notification-recipients` |
| 寄送邏輯 | 依 `topic` 取 `active = true` 的信箱；**清單為空時不寄送，改寫入 `notification_log` 並標記 `success = false`、`error = '無設定收件人'`** |
| 驗證 | Email 格式檢查；同一 `topic` 內不得重複 |
| 稽核 | 新增、修改、停用皆寫 `audit_log(action='setting_change')` |

> 收件人清單為空時**寫日誌而非靜默跳過**，否則「通知功能看起來正常但從來沒寄出去」會拖到月底才被發現，正是本案要消除的情境。
