# 長照交通接送後台系統 — 開發計畫與驗收條件

> 版本 v1.0 ／ 2026-08-25
> 前置閱讀：`01`～`03` 文件

---

## 1. 交付策略

客戶已同意分批交付，做完一部分即交付測試。

**時程參考點**：客戶每月 **27 日開始整理資料、次月 5 日前送件**。因此 M1 的目標是「趕上某一個月的申報週期」，並以該月的人工結果作為驗證基準。

| 里程碑 | 內容 | 估時 | 交付物 |
|---|---|---|---|
| **M1 政府申報表** | 主檔管理 + 表單匯入 + 申報表匯出 | 3–4 週 | 可用系統，能產出與人工版本一致的申報檔 |
| **M2 日常維運** | 未回報通知、異常處理、趟數表、新竹時刻表 | 2 週 | 每日自動化運作 |
| **M3 人事與車輛** | 維修保養、油資與出勤登錄、儀表板（不含薪資計算） | 2 週 | 內部管理功能 |
| **M4 薪資與記帳核銷** | F7 薪資表、每趟成本、利潤、核銷流程 | 規則到位後另估 | — |

## 3. M1 驗收條件

### AC-1 資料建檔（阻斷性）
- [ ] 全部在案個案、據點、車輛、司機皆已建檔，無缺漏欄位。
- [ ] 15 份 Google 表單皆已註冊，且所有 `ride` 欄位對應狀態為 `mapped` 或明確 `ignored`，`pending` 數為 0。

### AC-2 匯入正確性
- [ ] 匯入竹北一車 2026-05 全月資料，`ride_records` 筆數與人工計算一致。
- [ ] 竹南 2 車的四趟個案（如 `陳素貞(4趟)`），一日有搭乘時展開為 4 筆 leg。
- [ ] 混車個案（如 `*可能下午回竹1車載` 者）能跨兩份表單正確合併，且兩車皆回報有坐時進入衝突清單而非自動選一。
- [ ] 衝突經人工指定車輛與司機後，重新匯入同一份表單資料**不會覆蓋**該筆裁決結果。
- [ ] 罕用字（`吳𣵛桂`）、異體字（`劉温月妹` / `劉溫月妹`）不造成對應失敗或亂碼。
- [ ] 表單新增一個未知欄位時，資料仍完整存入 `form_submissions.payload`，且系統發出待對應通知。

### AC-3 匯出正確性（**核心驗收**）
- [ ] 以 115 年 7 月資料匯出個案「蔡曾切」，產出內容與客戶提供的 `蔡曾切11507.xls` **逐列逐欄完全一致**（39 列 × 33 欄）。比對儲存格值，不比對檔案格式（樣本為 `.xls`，系統產出 `.xlsx`）。
- [ ] 去程列的出發地為住家、目的地為據點；回程列相反。
- [ ] 服務日期為民國 7 碼，跨月、跨年正確。
- [ ] 隨機抽 5 位不同區域、不同趟數型態的個案，人工核對無誤。
- [ ] 兩位個案設不同單價與不同服務時長時，各自的第 6、10、11 欄正確反映該案設定。
- [ ] 服務時長跨小時的案例（如 09:55 + 10 分）第 10 欄正確進位為 `10`、第 11 欄為 `5`。
- [ ] 勾選某筆的「不申報 AA09」後，該列第 17 欄輸出 `1`，未勾選者維持空白。
- [ ] 產出的 `.xlsx` 檔案能**成功上傳政府線上系統**（須由客戶實測，是最終驗收）。

### AC-4 檢核與稽核
- [ ] 個案缺里程時，匯出被擋下並明確指出是哪一位、缺哪個欄位。
- [ ] 人工覆寫未填原因時，API 回 400 且資料庫不留下不一致資料。
- [ ] `allow_manual_override` 為 `false`（預設）時，覆寫 API 回 403，且前端不顯示覆寫入口。
- [ ] 稽核紀錄可查出「誰、何時、把哪一筆從沒坐改成有坐、原因為何」。
- [ ] 司機身分證與個案身分證同樣預設遮罩，reveal 動作留痕。

### AC-5 非功能
- [ ] 全部個案一個月的匯出在 30 秒內完成。
- [ ] 個案清單頁身分證預設遮罩，reveal 動作留痕。
- [ ] 資料庫每日備份已啟用並驗證可還原。

## 4. 測試策略

| 層級 | 範圍 | 工具 |
|---|---|---|
| 單元測試 | 民國日期換算、加解密、姓名正規化、合併演算法、33 欄對應 | Go `testing` + `testify` |
| **黃金檔案測試** | 以真實樣本 `蔡曾切11507.xls` 為期望值，比對系統產出 | Go golden file |
| 整合測試 | 匯入 → 合併 → 匯出全鏈路，跑真實表單樣本 | `dockertest` + Postgres |
| API 測試 | 權限、驗證、錯誤格式 | `httptest` |
| 前端 | 關鍵流程（欄位對應、覆寫、匯出） | Playwright（Vue SPA 以 E2E 為主，不寫元件單元測試） |

**黃金檔案測試是本專案最重要的一項**：把客戶提供的四份真實檔案放進 `testdata/`（**去識別化後**），任何邏輯改動只要讓產出偏離期望值就會立刻紅燈。

> ⚠️ `testdata/` 內含真實個案身分證與住址。**不可**直接放進 Git 儲存庫。作法：測試資料一律去識別化（身分證改為合法格式的假號、地址改為虛構地址、姓名改為代號），保留結構與邊界情況即可。原始檔案另存在客戶指定的加密位置。

## 6. 排除範圍（本階段不做）

明確寫出來，避免後續認知落差：

- 司機端 App 或網頁（司機繼續用 Google 表單）。
- 與政府平台的自動上傳串接（仍為人工下載檔案後上傳）。
- 個案地址／長照等級由政府平台自動同步（一律人工建檔）。
- 地址自動轉經緯度、里程自動計算（人工輸入；政府表單經緯度四欄維持空白）。
- 服務時長依里程自動推算（逐案人工維護）。
- LINE 推播（通知只走 Email）。
- 個案照顧計畫、服務紀錄等長照本業功能（本系統只處理交通接送申報）。
- 財務會計、發票、薪轉（M4 之後另議）。

## 7. 風險與緩衝

| 風險 | 緩衝作法 |
|---|---|
| 政府平台退件（文件 02 R-1） | Sprint 4 拿系統產出的實檔上傳驗證一次，不等到正式申報才發現 |
| R7 書面確認未到位 | 不影響 M1 開發：功能照做但旗標預設關閉，確認到位再開啟即可，無需改碼 |
| 表單改版後資料斷流（文件 02 R-2） | 逐車切換 + 每車送測試回覆驗證；`last_synced_at` 超過 48 小時未更新即告警 |
| 主檔缺欄位（單價／時長／四趟時段） | 這三類資料現有 Excel 都沒有，需客戶另補（協作事項 2、4）。批次匯入時以「使用預設值，請確認」標示，避免靜默帶錯 |
| 主檔建檔工作量被低估 | 提供批次匯入工具，並請客戶同步準備資料；此項排在 Sprint 2 起跑前 |
| 客戶需求擴張 | 每個里程碑結束時做範圍確認，新需求進 backlog 另估 |
| 單人開發、月底尖峰 | M1 上線後第一個申報月，維持**人工與系統雙軌並行**，比對無誤後才停用人工作業 |

> 最後一項很重要：**第一個月不要直接停掉人工作業**。讓兩者並行一輪，用實際結果證明系統正確，客戶才敢真正依賴它，出問題也有退路。
